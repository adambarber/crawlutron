## The defect

`app/api/main_helpers.py:31` builds the status response with a `**` splat of an
untyped record:

```python
def _build_job_status(row: dict[str, Any]) -> JobStatusResponse:
    return JobStatusResponse(**row)
```

`JobStatusResponse` declares `extra="ignore"` (`app/api_responses.py:365`), so any
key the record carries that the model does not declare is **discarded without a
word**.

The record it is given is `_status_row`'s 12-key projection
(`app/crawl/job_store.py:508`), which deliberately selects `kind` — and the
docstring there records that it selects it because two recovery seams depend on
it. The key is present in the store, present in the projection, and **absent
from every job status response the API has ever returned**.

Proven against the real store, not by reading:

```
row["kind"]            -> 'whole_site'
_build_job_status(row) -> hasattr(resp, "kind") is False
```

## Why 2566 passing tests never saw it

`dict[str, Any]` carries no key set, so every `row["..."]` read in the chain is
unchecked, and the `**` splat into a model with `extra="ignore"` is the type
check re-implemented by hand and discarded at the moment the value becomes a
dict. Nothing in the suite asserts the response carries `kind`, so nothing in
the suite can fail.

## Why it is the same defect that already shipped

The `_status_row` docstring (`app/crawl/job_store.py:500-506`) records a shipped
bug in this exact record: `kind` was missing from the projection, the rewind read
`summary.get("kind")`, the startup scan filtered on the same key, so every
summary answered `None` and **every job looked whole-site**. It was fixed by
adding the key by hand. The mechanism that let it ship was never removed, so the
same drift can ship again from any key.

`app/api/job_runner.py:149` still fails open on that key: `_is_resumable_kind`
returns True for `None`, so a summary that loses `kind` again retires nothing and
mis-resumes every single-shot job.

## The structural fix

Declare the record. A `TypedDict` for the status view makes every key read
checked and makes the splat bidirectional, verified against pyright:

```
19 reportCallIssue Unable to match unpacked TypedDict argument to parameters
```

With the view declared, a key the model does not declare stops being silently
dropped and becomes a compile error at the construction site — in both
directions, so neither producer nor consumer can drift alone.
