# AGENTS.md

This file provides guidance to agents working in this repository.

- The service is a stateless execution surface. Callers own frontier queueing, dedupe, persistence, and host-policy decisions; do not add caller state to the service to make a caller's problem easier.
- Agent/bot integrations should use the machine-readable discovery endpoints first (`/.well-known/crawler-service` and `/v1/capabilities`) and follow the durable contract in `docs/references/crawlutron-agent-contract.md`.
- It must not bypass Cloudflare or WAF controls, solve CAPTCHAs, rotate proxies or identities, inject credentials, or continue after an explicit denial. Terminal classifications are reported, not worked around.

## Agent dispatch rules (process)

- **Pre-development review before any feature or fix.** Read the ticket, the modules it touches, and the gates that govern them; state how the change fits the current architecture before writing code. A ticket whose body cites stale paths must be re-grounded from the live tree first.
- **Architectural review gate on tickets.** A GitHub ticket must carry an architectural review (its reach, its design choice, its walk-past plan) before an implementation agent picks it up. A quick `scripts/ticket_arch_review.sh <issue>` check assists the reviewer; it does not replace the review.
- **All development is TDD.** Red first for every behavior; record the red output; then green; then refactor. Budgets and ratchets move DOWN only, in the same commit as the work that earns them.
- **Gates seal shut at zero.** When a gate's offender count reaches zero, delete its budget/exemption table and leave an unconditional assertion — no configuration surface survives a sealed gate. Verify with a mutation check (inject the violation; the gate must name file and line).
- **Document process improvements here.** Any change to dispatch rules, review requirements, or gate doctrine is written into this section in the same commit that lands it.
- **Commit verification trap (2026-10-25, three occurrences):** never pipe a commit through `tail`/`grep` (the pipe swallows pre-commit's exit code — exit 0 with nothing landed); never compound `--no-verify` into a multi-statement command; after every commit attempt verify `git log -1` shows the expected message BEFORE proceeding.
- **Check `git status` before starting any change, and commit a small edit alone (2026-11-02):** an outstanding uncommitted migration/working tree on the same branch silently folds a sibling edit into a `git add -A` commit under the wrong ticket. Check for uncommitted work before editing; when present, land it separately first (if green) so the new change commits on its own, or stage only its hunks via `git add -p` / `git apply --cached`. A config-only change should never ride a 59-file migration commit.
- **Hook budget stays inside turn budgets (rewritten 2026-10-27, gate-speed audit):** every gate runs THROUGH `scripts/gate_fanout`, which starts all gate children at once on the first hook of a run and lets each hook wait only on its own child — wall time is the SLOWEST gate, not the sum. Each fan-out child is hard-killed after `WALL_SECONDS = 60` (`scripts/gate_fanout.py`), so no gate can hang a commit; a hang is a gate defect, never a reason to skip it. Measured on the reference machine (warm): full chain 15.9s — ruff 0.23s, ruff-format 0.17s, basedpyright ~2.8s (pyright until 2026-11-02, 4.28s; basedpyright uses the same config, fails close on a dead include), jscpd 0.17s, mypy 0.17s, vulture 0.18s, safety-invariants 10.0s (`-n 6` xdist; serial 35.6s; slowest legit invariant 3.3s). Every gate still runs on every commit — exclusion, `--no-verify`, and budget raises are forbidden; the jscpd floor tightened 3/30 → 2/30 in the same audit (zero pairs measured over 687 sources). When a gate or invariant test is added, the chain must stay fast enough for a subagent to complete a commit inside one turn; if the warm chain grows past ~25s, parallelize further rather than trimming tests. A cold chain (fresh workspace, no `.mypy_cache`/`.gate_fanout`) is the number a subagent hits on workspace up — keep it under ~60s or pre-warm caches in the workspace setup steps.
- **Subagent dispatch protocol (user directive 2026-10-27, mandatory for every dispatch):** the FIRST thing a dispatched subagent does, before any other work, is validate its environment: (1) confirm `git rev-parse --show-toplevel` and `git branch --show-current` name its assigned hardstand workspace and `work/*` branch — never main, never another writer's workspace; (2) confirm its tools work (`.venv/bin/python` resolves, `pytest` collects, pre-commit hooks are installed); (3) confirm it has the ticket context, directions, and workspace path it needs. If ANY check fails, it MUST send the parent a message describing the failure and HALT until it receives direction — zero improvisation, zero workspace-hopping. Additionally, every subagent ENDS every turn with a SELF IMPROVEMENT REVIEW: what its instructions failed to cover, what process friction it hit, and what the parent should change to make the next dispatch succeed. The child writes it into its final report text (child sessions have no ctx_memory tool); the parent reads every review and folds accepted improvements into this section — the improvement cycle is part of the dispatch itself, not an afterthought. Dispatch-prompt checklist for the parent, from accumulated reviews: name how to read CLOSED issues (`state:"all"`), tell writers to run `ruff check` AND `ruff format --check` before committing (blocked commits are the gate working — never auto-fix to mask them), and state the expected layer/package for ownership moves rather than leaving it to the writer's judgment (the venv-PATH caveat for test_repo_tool_resolution is obsolete — the fixture pins the interpreter's bin onto PATH itself, commit ef5b9996 follow-up). Workspace commands run through HARDSTAND, not bare shell cd+PATH chains (owner directive 2026-10-28): declared actions — `hardstand run <ws> pytest-fast`, `hardstand run <ws> mypy`, `hardstand run <ws> ruff`, `hardstand run <ws> typecheck` — get the declared env and explicit timeouts; arbitrary one-offs via `hardstand exec <ws> -- <argv>`; NEVER `cd .hardstand/<ws> && PATH=... <tool>` by hand (unmanaged env, no timeout, no declared keys). For type-checker evidence prefer adding a declared action in hardstand.toml over shell chains.. Pre-flight additions (2026-10-27, BU review): every writer merges main FIRST (`git merge main --no-edit`) — ticket-referenced files may have moved since the branch diverged; grep tests/ and docs/ for a source path string before any `git mv` (four path-pinning invariants need same-commit edits); tools with path parameters get ABSOLUTE in-workspace paths (ast_grep_replace resolves against the parent checkout otherwise). Further additions (2026-10-27, BV review): "re-derive the defect from the live tree before coding" is a standard clause on every bug ticket — a ticket's prescribed fix may be architecturally wrong (BV proved it on #560); after a failed issue-tool write, verify via a read before retrying, and if reads also fail, note the attempt and STOP writing (outcome-unknown writes are untracked state); degraded-mode writes use a bounded cadence — at most one retry per major work phase, never a loop — and report tool-reported success as UNVERIFIED until a read confirms. On degraded GitHub, writers pre-authorize commits citing the ticket number from the dispatch (commit-msg gate needs it); the parent reconciles bodies when GitHub recovers. BW additions (2026-10-27): new detector/gate tests must themselves be gate-clean — public app doors only, docstrings ≤3 lines, no clone-pairs between sibling tests — extract the shared sweep before committing; when the private-imports gate blocks a test, the fix is a public door (rename + `__all__`), not an exemption; mutation checks on AST gates are done with in-memory AST probes, never shelling a mutated tree (stale pycache corrupts collection and can't be cleanly undone); mutation checks on RUNTIME code use a scratch-dir tree copy (mutate the copy, pytest the copy, discard) — never mutate the workspace in place. Dispatch prompts state the comment limits up front (≤2-line comment runs, ≤3-line docstrings) and say "check whether X already landed" for work whose dependencies recently merged; multi-hundred-line rewrites go through whole-file write from the git base, not line-range edits (a bad range can truncate the file tail); the same rule binds any edit spanning >20 lines. CA additions (2026-10-28): `ls tests/_*.py tests/invariants/_*.py` before creating a support module (two existing helpers were clobbered by name collision); run the jscpd gate locally before committing extraction/move work (clone-pairs with leftover originals are the predictable failure); moved code must be type-clean in its new home — mypy scope covers tests/**/_*.py even if the source test module was never checked; when repointing test doubles, preserve call signatures, not just import lines; probe GitHub degradation with a READ (show_issues), never a write.
- **Workspaces never diverge (user directive 2026-10-27):** a settled writer's branch merges into local main BEFORE the next writer dispatches into that workspace — no long-running diverging workspaces. The parent audits divergence (`git rev-list --count main..work/<name>` and `HEAD..main`) at every dispatch and every merge; a workspace found ahead of main unmerged is landed immediately (battery-verified) before new work. A writer starting in a shared workspace runs `git merge main --no-edit` as its first act.
- **Hardstand adoption mandate (user directive 2026-10-24):** all implementation agents run inside their hardstand workspace only (config: hardstand.toml, workspaces under `.hardstand/` INSIDE `~/Projects/crawlutron` on `work/*` branches, venv via `ln -sfn ../../.venv .venv` symlink, zero downloads). Agents that hit blockers (tests not working, etc.) must message the parent and WAIT for guidance, never self-resolve by leaving the workspace or editing main. The parent is the sole responsible agent for enforcing adoption/compliance — fix hardstand if broken, do not abandon it. All 8 pre-commit hooks must work correctly INSIDE each workspace and BLOCK commits until green — verify by planting a violating commit (e.g. overlong docstring) inside a workspace and proving pre-commit refuses it, then a clean commit lands.
- **Magic comments are banned (standing law, owner directive 2026-11-05):** no `# noqa`, no `# type: ignore`, no inline lint/type-checker suppression of any kind may ever land in main. Checker complaints are resolved structurally (typed exception handling, guards, Protocol splits, signature widening, provenance-documented named casts) or the code is restructured. Typeless third-party packages get a `[mypy-<package>.*]` config section with written justification, never an inline ignore. Fabricated import-failure fixtures that disable the type checker are likewise forbidden — drive real seams via typed stubs (a real `types.ModuleType` that keeps sibling imports alive while removing the one symbol under test), never `__getattr__` suppression. Applies to every dispatch prompt: state the ban up front; reviewers reject any commit introducing a suppressor.
- **Test changes carry standing approval with a plan message (owner directive 2026-11-05):** writers may freely change tests when the change covers the same behavior and improves the codebase — no per-change permission. When significant test changes are required (rewriting many tests, replacing an assertion strategy, refactoring shared test infrastructure), the writer FIRST sends the parent a message explaining the plan — scope transparency, not permission-seeking. Do not contort production or test code (cast-soup, duck-typed shims, stringly-keyed override dicts fed to `dataclasses.replace(**...)`) to avoid touching tests: the wave4c precedent (`replace(absent, **cast("dict[str, Any]", coerced))` hid a hand-maintained coercion ladder and erased mypy's per-field checking) is the named failure. Reviewers treat unexplained large test rewrites as reportable scope concerns, not defects, when behavior coverage is preserved or improved.
- **Hardstand down is the sanctioned teardown (CLI updated 2026-11-05):** `hardstand down <name> --merge` lands the branch into base before teardown — merging is opt-in via the flag (never default), plain `hardstand down <name>` prints a plan + digest, destroys nothing, and refuses unmerged/uncommitted work; `--apply <digest>` executes the plan; `--concede-uncommitted` exists for genuinely uncommitted work. Manual merge/teardown chains are no longer required; still required: battery green before passing `--merge`, check `hardstand list` held-state first, full suite + gate after any merge (seam risk).
- **Regression bar on suite shape (owner directive 2026-11-05):** the parallel suite's test count and wall time (3,431 passed in ~16s at the baseline) are regression-guarded — any test-count increase or significant wall increase is a regression; writers halt and flag it, never absorb it. Known-flaky tests are inventoried in a flake ledger the parent maintains; every observed flake gets a tracked ticket and a root-cause fix (never masked, never timeout-raised) before suite work is complete.
- **Parent-side issue sync on degraded network (owner directive 2026-11-05):** host `gh`/git-to-github dies (TLS timeout); the working path is the Docker bridge + the host macOS keychain PAT: probe with a READ first (never a write), file/close/comment issues via `docker run --rm -e GH_PAT python:3-alpine` + curl against `api.github.com/repos/<owner>/<repo>`, then independently VERIFY every write with a read before relying on it. Parent maintains the authoritative open-issue list by reading GitHub, not from memory.
- **Reviewer escalation ladders (accumulated 2026-11-05):** a false claim in a writer's report (commit says "deleted" but nothing was deleted) is an automatic REQUEST_CHANGES regardless of materiality. Reviewers verify writer claims against the live tree (commits, diffs, file presence) — completion notices are hypotheses. Security-adjacent work gets a total-coverage sweep: every sink (log paths, metric labels, delivery bodies, error envelopes, exception messages, dumps, records, API responses) scanned for the sensitive class, plus an adversarial attack on the chokepoint itself (encoding tricks, ordering races, bypass shapes). Speculative-hardening reviewer suggestions are rejected unless a concrete victim exists; dead surface found during review is deleted in the writer's fix round.
- **Object-invariant secrets (owner directive 2026-11-05, #599 shape):** secrets enter an object via its constructor and never surface unless explicitly and intentionally used — redaction is an object invariant (redacted-by-default projections; a named, intention-revealing accessor at the point the credential is genuinely consumed), not a call-site chore every new caller must remember. Secrets-in-URLs are refused at the model chokepoint (NormalizedUrl rejects userinfo; credentials live origin-scoped in policy.credentials); the wrapper object (e.g. WebhookTarget) holds the SSRF-admitted NormalizedUrl privately. No `Object | str` unions at boundaries — the object is the type; str→object conversion happens once at the outermost admission edge.
- **Global hard timeout on the test suite (owner directive 2026-11-06):** `timeout = 120` in pytest.ini is a two-minute ceiling on every pytest invocation everywhere (writers, reviewers, parent) — a red run against a hang/spin defect must FAIL naming file+line, never hang the host (2026-11-06 incident: a wave4b red run of the #619 disconnect-spin test hung 14 xdist workers at 100% CPU until killed; same fingerprint as the morning panic-adjacent runaway). ONLY the owner authorizes an increase — including any per-test override above the global. Tests that exercise a hang/spin defect must be written hang-safe: bound the wait (asyncio.wait_for) and assert the bound is exceeded, so the red is a failure, never an indefinite hang. Targeted pytest runs bypassing declared hardstand actions MUST also be bounded (timeout command or hardstand exec).
