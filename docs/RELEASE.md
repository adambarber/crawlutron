# Release runbook

The version lives in a git tag, nowhere else. `[tool.hatch.version] source = "vcs"`
in `pyproject.toml` resolves it from the newest tag at build time, and the
generated `packages/core/src/crawlutron/_version.py` is a gitignored build
artifact. There is no hand-edited version and no second place that records one.

SemVer, honest `0.MINOR.PATCH` until 1.0 (minor may break), matching the
`Development Status :: 4 - Beta` classifier.

## Cutting a release

```sh
git tag v0.5.0
git push --tags
```

That is the whole act. Pushing the tag is what creates the release: CI derives the
version from the tag, asserts every artifact carries it, and publishes.

## What CI does with the tag

`.github/workflows/release.yml` triggers on `v*` and runs three jobs:

| Job | Publishes | Guard |
|---|---|---|
| `distributions` | every member (sdist + wheel) to **PyPI** | asserts each sdist's version equals the tag, then `twine check --strict` |
| `image` | the `runtime` image to **GHCR** as `:{version}` and `:latest` | runs the pushed image, asserts the baked `crawlutron.__version__` equals the tag |
| `github-release` | a **GitHub release** with autogenerated notes and a CycloneDX SBOM | needs both jobs above to have succeeded |

A tag that does not match the tree fails the first job before anything is
uploaded, so a mis-tag can never ship `0.0.0.dev0` under a semver name.

## Packaging is checked on every commit

`.github/workflows/packaging.yml` runs on push and pull request and publishes
nothing. It builds every member, inspects every artifact with `twine check
--strict`, installs each wheel into its own clean 3.14 environment, and imports
its top level (the import name comes from the installed metadata, because
`crawlutron-safe-url` imports as `safe_url`). It also builds the container image
without pushing. A packaging break therefore reds before merge, not at release.

The same probe is runnable locally: `uv build --all-packages --out-dir dist` then
`.venv/bin/python scripts/check_packaging.py`.

## One-time PyPI setup (owner)

Publishing uses **trusted publishing** (OIDC): there is no stored token, and the
workflow identity is the credential.

PyPI dedupes *pending* publishers on the workflow identity, and each pending
publisher is bound to one project name and consumed by that name's first upload. So
the names cannot all be pre-registered: register one, release, register the next.

To avoid six release cycles, bootstrap instead: create a scoped PyPI API token,
add it as the repository secret `PYPI_API_TOKEN`, and push the tag. The release
job publishes with the token while the secret is set and with trusted publishing
when it is not. Once every name exists, add each project's trusted publisher (owner
`adambarber`, repository `crawlutron`, workflow `release.yml`, environment `pypi`)
and delete the secret.

The environment `pypi` already exists in this repository with a tag-only
deployment policy; add required reviewers there if a release should need a human
click.

## What was removed

`.github/release-please.yml`, `release-please-config.json` and
`.release-please-manifest.json` are deleted. release-please never ran: the file sat
in `.github/`, but Actions loads workflows only from `.github/workflows/`, and even
relocated it could not work — `release-type: python` edits a static `version`
field, while this project's version is `dynamic` with a `vcs` source. Its manifest
claimed `0.3.2` while the only tag was `v0.4.0rc0`. Keeping it meant two sources of
truth for one fact.

**Escape hatch, documented rather than built:** if release automation is ever
wanted, it must derive the next version from the tag plus commit subjects and
*propose a tag* — never write a version field, and never become a second place the
version is recorded.

## Commit format (commit-msg gate)

`scripts/commit_citation_gate.py` runs at commit-msg and enforces three laws, each
refusal naming the law that fired:

- **Citation**: every commit cites an issue (`Closes #N`).
- **Format**: subject is a Conventional Commit, `type(scope): ...` with type in
  feat/fix/docs/chore/refactor/test/build/ci/perf.
- **Schema**: a `feat!` touching
  `packages/core/src/crawlutron/models/crawl_policy.py` must bump
  `POLICY_SCHEMA_VERSION` in the same commit.

`CHANGELOG.md` and `CHANGELOG-legacy.md` are the existing history;
`CHANGELOG-legacy.md` preserves the pre-automation record verbatim. GitHub release
notes are generated from the commit log (`gh release create --generate-notes`).
