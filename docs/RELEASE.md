# Release runbook

The version lives in a git tag, nowhere else. `[tool.hatch.version] source = "vcs"`
in `pyproject.toml` resolves it from the newest tag at build time, and
`packages/core/src/crawlutron/_version.py` is **tracked in git** so every checkout
has it before any gate runs; hatch-vcs overwrites it at build time. There is no
hand-edited version and no second place that records one.

SemVer, honest `0.MINOR.PATCH` until 1.0 (minor may break), matching the
`Development Status :: 4 - Beta` classifier.

## Cutting a release

```sh
git tag v0.5.0
git push --tags
```

That is the whole act. Pushing the tag is what creates the release: CI derives the
version from the tag, asserts every artifact carries it, and publishes.

## What CI does with the tag

`.github/workflows/release.yml` triggers on `v*` and runs the guard, then one matrix job per distribution, then the image and GitHub-release jobs:

| Job | Publishes | Guard |
|---|---|---|
| `guard` | nothing (gate only) | builds every member, asserts each sdist's version equals the tag, then `twine check --strict` |
| `distributions` | one member per matrix job (sdist + wheel) to **PyPI** | needs `guard`; builds only its own package, `twine check --strict`, uploads only its own `dist/` |
| `image` | the `runtime` image to **GHCR** as `:{version}` and `:latest` | runs the pushed image, asserts the baked `crawlutron.__version__` equals the tag |
| `github-release` | a **GitHub release** with autogenerated notes and a CycloneDX SBOM | needs `distributions` and `image` to have succeeded |

Publishing is one matrix job per distribution with `max-parallel: 1`, so uploads
are spaced by job startup instead of bursting the roster at PyPI and hitting the
429 rate limit that lost `crawlutron-safe-url` and `crawlutron-sdk` in run
43535563524. A re-run of a failed matrix job publishes only that distribution --
there is no third-party retry action; the matrix itself is the retry.

A tag that does not match the tree fails the first job before anything is
uploaded, so a mis-tag can never ship `0.0.0.dev0` under a semver name.

## Packaging is checked on every commit

`.github/workflows/packaging.yml` runs on push and pull request and publishes
nothing. It builds every member, inspects every artifact with `twine check
--strict`, installs each wheel into its own clean 3.14 environment, and imports
its top level (the import name comes from the wheel's own `__init__.py`
contents, not installed metadata, so `crawlutron-safe-url` imports as
`safe_url`). It also builds the container image without pushing. A packaging break therefore reds before merge, not at release.

The same probe is runnable locally: `uv build --all-packages --out-dir dist` then
`.venv/bin/python scripts/check_packaging.py`.

## One-time PyPI setup (owner)

Publishing uses **trusted publishing** (OIDC) only: there is no stored token,
and the workflow identity is the credential. The `PYPI_API_TOKEN` bootstrap
fallback was removed — there is no long-lived PyPI credential in this repository.

Each project needs one trusted publisher configured on pypi.org. Pending
publishers are deduplicated on the workflow identity and bound to one project
name, consumed by that name's first upload. Register one, release, register the
next: owner `adambarber`, repository `crawlutron`, workflow `release.yml`,
environment `pypi`.

The `pypi` environment already exists in this repository with a tag-only
deployment policy. **Required reviewers must be added to the `pypi` environment**
so no release publishes without a human click.

## Release security requirements

These are enforced outside the repository (GitHub repo settings) and must be in
place before the first release:

- **Branch protection on `main`**: requires a passing CI `required` check and a
  pull request review from a release owner before any merge.
- **Tag protection on `v*`**: only release owners may create or push `v*` tags.
  A tag is the release act — unrestricted tag pushes bypass CI gating entirely.
- **CODEOWNERS**: `.github/CODEOWNERS` lists release-owning paths
  (`.github/workflows/release.yml`, `.github/actions/prepare/action.yml`,
  `scripts/release_roster.py`, `docs/RELEASE.md`); changes to those files
  require release-owner review.
- **`pypi` environment required reviewers**: ≥1 release owner must approve every
  publish.

## What was removed

`.github/release-please.yml`, `release-please-config.json` and
`.release-please-manifest.json` are deleted. release-please never ran: the file sat
in `.github/`, but Actions loads workflows only from `.github/workflows/`, and even
relocated it could not work — `release-type: python` edits a static `version`
field, while this project's version is `dynamic` with a `vcs` source. Its manifest
claimed `0.3.2` while the only tag was `v0.4.0rc0`. Keeping it meant two sources of
truth for one fact.

**Escape hatch, documented rather than built:** if release automation is ever
wanted, it must derive the next version from the tag plus commit subjects and
*propose a tag* — never write a version field, and never become a second place the
version is recorded.

## Commit format (commit-msg gate)

`scripts/commit_citation_gate.py` runs at commit-msg and enforces three laws, each
refusal naming the law that fired:

- **Citation**: every commit cites an issue (`Closes #N`).
- **Format**: subject is a Conventional Commit, `type(scope): ...` with type in
  feat/fix/docs/chore/refactor/test/build/ci/perf.
- **Schema**: a `feat!` touching
  `packages/core/src/crawlutron/models/crawl_policy.py` must bump
  `POLICY_SCHEMA_VERSION` in the same commit.

`CHANGELOG.md` and `CHANGELOG-legacy.md` are the existing history;
`CHANGELOG-legacy.md` preserves the pre-automation record verbatim. GitHub release
notes are generated from the commit log (`gh release create --generate-notes`).

## Deferred

Deploy, fleet concerns, and the Homebrew / npx channels are out of scope per the
#561 owner ruling.

Image signing (Cosign + SLSA provenance) and atomic publish / rollback
(github-release as the commit point with rollback on partial failure) are
deferred. They are documented escape hatches: when release automation reaches
that maturity, add Cosign signing to the `image` job, SLSA provenance to both
publish jobs, and make `github-release` the commit point so partial-publish
states (PyPI published, image not, or vice versa) cannot persist. Until then,
partial-publish recovery is manual: inspect `distributions` and `image` job
results before trusting a release.
